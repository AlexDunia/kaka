1. Scope and how to read this report

This inventory follows the active frontend: opening an event, the organiser
dashboard, ticket details, promotions, discounts, messaging, door check-in,
earnings, settings, editing, public ticket selection and issued tickets.
It describes current working files, including uncommitted changes. No live
orders, check-ins, messages, withdrawals or event changes were submitted.

API-connected means a frontend request exists; it does not prove the endpoint
works in production. Development preview means fixtures replace dashboard API
data. Static sample means values are hardcoded even in production. Local
interaction means browser state, navigation or clipboard rather than a database
write. Backend storage and calculations were not independently verified.

2. The main finding: implemented data and sample screens coexist

Overview and Promote have API service paths. Development currently enables
DASHBOARD_PREVIEW = import.meta.env.DEV && true in
src/services/dashboardPreview.js. It replaces dashboard event list, overview and
sharing-link reads with fixture data during npm run dev.

Attendees, Discount codes, Message attendees, Door check-in, Earnings and
Settings are static Vue templates. They have no script, event-specific props,
API reads or mutation handlers. Their sample values do not follow the selected
event. Disabling preview does not connect these screens.

Door check-in currently does not scan or validate tickets. Discounts does not
create codes. Messaging does not send email. Earnings does not withdraw money.
Settings does not pause, cancel, delete or refund an event. These are visible
interface designs, not completed operational features.

3. Opening an event: public versus organiser experience

Public event cards route through useSlug.getEventUrl to the public event page.
/events/:id-:slug and legacy /event/:id render src/pages/EventDetails.vue.
Attendees can read details, select tickets, share, like and enter checkout.

/dashboard and /dashboard/events/:eventId render src/pages/Dashboard.vue.
Both require authentication and use a full-screen organiser shell with sidebar,
topbar and selected management view. Overview is the initial view.

The sidebar My Events back link currently routes to '/', not to a separate
organiser event-list screen. Event switching happens in its sidebar dropdown.
The signed-in account menu outside the dashboard links to /dashboard.

5. Dashboard loading, selection, cache and errors

Sources: src/pages/Dashboard.vue, src/stores/dashboard.js,
src/services/dashboardService.js.
Outside preview:
  GET /api/dashboard/events -> response.data.data array.
  GET /api/dashboard/events/{id}/overview -> response.data.data object.
Requests use the central credentialed Axios client.

Positive integer route eventId is preferred, otherwise first event ID. The route
is checked against the returned owned-event list; absent/unrecognized IDs are
replaced with the first owned event's dashboard URL. This is frontend selection,
not a substitute for backend ownership checks.

Switching event closes dropdown, resets view to Overview, changes route and
loads its overview. Events cache in Pinia after successful load unless forced.
Overview caches per event with a 30-second freshness TTL. TTL is checked when
fetchOverview runs; it is not an automatic refresh interval.

There is no dashboard polling, WebSocket or server-sent-event subscription.
Live data copy does not imply continuous updates. Full reload clears memory.
Active view is component state, not a URL tab/query; reload normally resets it.

Loading: DashboardContentSkeleton while events/overview load.
Failure: error card, error message and Try again action.
No events: No events yet, explanation and Create event button.
Overview must exist before any DashboardManageContent child view renders.
Source TODOs mention distinct no-events/no-sales/no-traffic/no-attribution states
still needing design after preview review.

23. Public ticket cards: mapping and fallback inventory

event.ticketTypes array maps each item:
  ID from lowercase name/spaces to hyphens, not necessarily backend type ID.
  Name or Ticket N; description or '<name> admission ticket'.
  price parsed number, formatted NGN.
  availableQuantity from quantity || 0; available when >0.
  Sold Out when unavailable; Only N left when <=5; normal buy action otherwise.
  Rotating icon style; highest-priced tier(s) get Popular, not highest sales.
  Table detected by word table in name, not unitType.
  Seats parsed from 'table for N', else table default 4.
  Table badge/seat count; mapped maxPerPurchase 2 tables, otherwise 10.
  Modal does not enforce that mapped max; it uses global quantity 1-10.

If ticketTypes is absent/not array, frontend invents:
  Standard base price, regular admission, max 10.
  VIP base*1.5, premium seating + complimentary drink, max 6.
  Table for 4 base*3.6, reserved 4 seats, max 3.
  Table for 8 base*7, reserved 8 seats, max 2.
All fallback choices marked available; highest price Popular. They are not
proof backend inventory exists. Empty array yields no cards, not fallback.

Expired sales replace grid with sales-ended date/explanation. Opener checks
expiry. Sold-out button is disabled, but card retains click handler and opener
does not separately check availability. Backend must validate actual stock.

24. Quick Purchase modal and cart handoff

Ticket click uses 300ms debounce plus 50ms modal delay.
Modal shows image/title, date/event.location, chosen type/unit price, quantity
minus/plus 1-10, total price*quantity, cart and QR actions, close/outside-click.
Cart object:
  eventId,eventTitle,eventDate,eventLocation,ticketType,ticketId,quantity,
  pricePerTicket,totalPrice,eventImage.
Location fallback address.venue_name -> location -> Venue TBA.
Add closes modal/reset quantity then toast and /checkout navigation after 4 sec.
Toast reads quantity after reset, so can say 1 even for larger stored quantity.
No payment or issued ticket is created by this cart action. Backend quote is
the authority for real pricing/inventory, not the public fallback cards.

Important current integration mismatch: src/stores/cart.js requires eventId,
ticketId and quantity to convert to integers. Public EventDetails generates
ticketId from names such as general-admission or standard. Those convert to
NaN, so addItem silently returns without adding an item, while the public page
still shows its success toast and proceeds toward checkout. This can leave an
empty cart. The handoff above describes the attempted submission; it is not a
guarantee that the cart accepts it. Real numeric backend ticket-type IDs must
agree across event response, selection and cart for the path to work.
Checkout items are mapped to {ticket_type_id:Number(ticketId),quantity}.
Cart is sessionStorage-backed, merges by eventId/ticketId, sums quantity/total,
and invalidates the checkout attempt when contents change. This is separate
from issued order-ticket storage.

  Encodes origin + /event/{id}?ticket={derived-type-id}.

  Revisits ticket selection; not paid admission entitlement.

Issued QR in PaymentSuccess.vue:
  Encodes backend ticket.token for paid order; public_id and optional admits.

  Decorative divs, no payload/scanner/download.
First two do not make the third a working admission system.

    remembers token and clears cart appropriately.
Order endpoints:
  GET /api/checkout/orders/{orderId}.
  POST /api/checkout/payments/{reference}/verify (CSRF).
  Optional X-Checkout-Token header.
sessionStorage keys checkoutAttemptToken and checkoutOrderToken:{orderId}.
These are order access tokens, separate from Google/authentication session.

PaymentSuccess.vue, /payment-success/:orderId:
  Confirming payment loading; optional reference/trxref query verifies first,
    then order fetch on failed verification.
  paid: confirmation, grouped event titles, ticket name, ticket.public_id,
    Admits N if admit_count>1, ticket.token QR size 112 rendered SVG.
  payment_review: payment received/checking availability, Check status.
  other pending: still confirming, Check again.
  forbidden/missing/generic order errors and Back to events.
Actual paid tickets are not loaded into the static organiser Attendees/Door
screens. Webhooks, locks, payment verification and admission security require
backend inspection; frontend display does not establish those guarantees.
